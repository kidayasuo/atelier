# 会話を軽くする決まり（効率化委員会、10-28）

どのチャットも、役割分担の次にこれを読む（約2,500字）。

**なぜ重くなるか**（西館係の測り、10-27、作業 約250回）：ファイルの作業 44%・チャットへの指示（約16万、作業のたびに読み直される）35%・プロジェクトの文書 11%。作業1回ごとに、指示とそれまで会話に入ったもの全部が読み直される。だから効くのは、**作業の回数を親のチャットから外す**ことと、**会話に入れる量を減らす**こと。

## 1. 手を動かす作業はサブエージェントに出す（いちばん効く）
- 親のチャットが持つのは、ユーザーとの相談・判断・結論だけ。スクリプトを広く読む／直して作り直しを確かめる／ログや図を調べる、の繰り返しは **Agent（general-purpose）に一つの頼みとして出す**。中の数十回の作業は親の会話に入らず、親の指示（16万）も読み直さない。親に戻るのは報告だけ。
- 頼みの文に書くこと（サブエージェントは会話を知らない）：
  1. 場所と担当（例：西館係の `south/add_monitor_west.py` の母屋）
  2. 決まったこと（数・寸法・ユーザーの言葉。決定事項から要る行だけ写す）
  3. 直してよい範囲と、直してはいけない所（ほかの係の節・分冊・作ったもの）
  4. 確かめ：`bash tools/tsukuru.sh` の check の行が「通った」、✗ が無い
  5. commit（頭は親の担当）と push まで／push しないで報告、のどちらか
  6. 報告の形：**300字以内**（直したファイル・commit・check の行・判断が要った所）。ログや画像は貼らない、ファイルの場所だけ
- **判断が要る所が出たら、サブエージェントは止まって報告する**（勝手に決めない）。親がユーザーに聞き、続きは SendMessage で同じサブエージェントに（読んだものを持ったまま続く）。
- 一度に一つの場所に一つ（同じファイルを二つが直さない）。走らせている間も、親はユーザーと話せる。
- 報告を鵜呑みにしない：親は check の行と `git show --stat` だけで確かめる（中身を丸ごと読み直さない）。

## 2. 会話に入れない
- 作り直しの確かめは `bash tools/tsukuru.sh`（ログはファイルへ、出すのは check の行と止まった所だけ）。Bash の run_in_background で走らせ、終わりの知らせを待つ。途中で何度も覗かない。
- 長い文書は見出しから：`python3 tools/yomu.py <file>`（見出しと字数）→ `python3 tools/yomu.py <file> 見出しの一部`（その節だけ、`--grep 語` で行だけ）。
- スクリプトは `grep -n` で場所を探し、Read の offset・limit で要る所だけ。一度読んだ所は会話に残っているので、二度読まない。
- 図は縮めた画像（長辺 1600 px 以下）を、確かめたい所だけ切り抜いて1枚ずつ。見比べのために何枚も取り込まない（見比べはサブエージェントに）。
- 書いたファイル・文書を、確かめのために読み直さない（Edit・Write は失敗すれば知らせる）。

## 3. 決定事項は直す所だけ
- 10-28 から決定事項はリポジトリの `kettei/` が本文（共通は `kyoutsu.md`）。読むのは `tools/yomu.py` で節だけ、書くのは Edit で直す所だけ（全文を読み直して全文を書かない）。
- プロジェクトの文書は写し。写しを作るときは `project_write` の `local_path`（中身が会話に入らない）。

## 4. 頼みが変わったら新しいチャット
- 一つの頼みが済んで、次の頼みが別の場所・別の作業（壁 → 屋根の形 → 大きさ）なら、新しいチャットで始める方が軽い。決まりを書いて push しておけば、引き継ぎは要らない（新しいチャットは決定事項と git log を読む）。
- 重さを測りたいときは `explain-usage`（このセッションの量の内訳）。
