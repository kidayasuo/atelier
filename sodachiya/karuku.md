# 会話を軽くする決まり（効率化委員会、10-28）

どのチャットも、役割分担の次にこれを読む（約2,500字）。

**なぜ重くなるか**（西館係の測り、10-27、作業約250回）：ファイルの作業 44%・チャットへの指示（約16万、作業のたびに読み直される）35%・プロジェクトの文書 11%。作業1回ごとに、指示とそれまで会話に入ったもの全部が読み直される。だから効くのは、**作業の回数を親のチャットから外す**ことと、**会話に入れる量を減らす**こと。

## 1. 手を動かす作業はサブエージェントに出す（いちばん効く）
- 親のチャットが持つのは、ユーザーとの相談・判断・結論だけ。スクリプトを広く読む／直して作り直しを確かめる／ログや図を調べる、の繰り返しは**Agent（general-purpose）に一つの頼みとして出す**。中の数十回の作業は親の会話に入らず、親の指示（16万）も読み直さない。親に戻るのは報告だけ。
- **図を描く仕事も同じ**：描く→画像で確かめる→直す、の繰り返しはサブエージェントに。親がユーザーに見せるのは、仕上がった図（と、判断が要る所）だけ。ユーザーの直しの言葉は、親がまとめて同じサブエージェントに SendMessage で渡す。
- 頼みの文に書くこと（サブエージェントは会話を知らない）：
  1. 場所と担当（例：西館係の `south/add_monitor_west.py` の母屋）
  2. 決まったこと（数・寸法・ユーザーの言葉。決定事項から要る行だけ写す）
  3. 直してよい範囲と、直してはいけない所（ほかの係の節・分冊・作ったもの）
  3b. **形の作り方**（3dmに物を足す・作り直すとき。10-31、ユーザー：毎回「これは直方体であるべき」と言い直している）：板・梁・柱・壁・ガラスの帯・家具の箱は、**直方体か、一つの平らな輪郭をまっすぐ押し出した形**（穴は内側の輪郭、開口は引き算）で作る。三角形を並べたメッシュで作ってよいのは、決めてある自由な形（クスノキ・地形・丘・雨の川）だけ。曲がった物は円柱・円弧の押し出しで。迷ったら作る前に親に聞く。決まりの元は`kettei/kanshu.md`の点検の7（形が素直）と`model/build/SOLIDS.md`
  4. 確かめ：途中は**直した段のスクリプトと小さな測り**（`tools/hakaru.py`）だけ。通しの`bash tools/tsukuru.sh`（30〜40分）は**一連の直しが全部済んでから1回**、check の行が「通った」、✗が無い（下の2）
  5. commit（頭は親の担当）と push まで／push しないで報告、のどちらか
  6. 報告の形：**300字以内**（直したファイル・commit・check の行・判断が要った所）。ログや画像は貼らない、ファイルの場所だけ。**同じ報告を`renkei/files/report_<日時>_<係>.md`にも書いておく**（セッションが作り直されても消えない。push はしなくてよい）
- **判断が要る所が出たら、サブエージェントは止まって報告する**（勝手に決めない）。親がユーザーに聞き、続きは SendMessage で同じサブエージェントに（読んだものを持ったまま続く）。
- 一度に一つの場所に一つ（同じファイルを二つが直さない）。走らせている間も、親はユーザーと話せる。
- **同時に二つ以上の作業役を走らせるときは、作業フォルダを分ける**（Agent の `isolation: "worktree"`、または `git worktree add`）。同じフォルダだと、片方の途中のファイルがもう片方の commit に混じる（10-30、26eae56）。どの作業役も commit は**自分が直したファイルだけ**`git add <path>`（`git add -A`・`.` は使わない）。
- **作業役のモデル**：判断の要らない作業役（作り直しの確かめ・寸法を測る・ログを調べる・受け箱や知らせの片づけ）は、Agent の`model`に`sonnet`（ごく機械的なら`haiku`）を指定する。形や納まりを考える作業役は指定しない（親と同じ）。
- 報告を鵜呑みにしない：親は check の行と `git show --stat` だけで確かめる（中身を丸ごと読み直さない）。

## 2. 会話に入れない
- **通しの作り直しは、一連の直しの最後に1回**（10-31、ユーザー：直すたびに作り直すのは無駄）。段は順につながっていて、前の段（西館の架構＝段0など）を直すと全部の段が作り直しになり30〜40分かかる。途中の確かめは：
  - 直した段のスクリプトだけを走らせる（どの段が何を読むかは`model/build/stages.md`）。後ろの段だけを直したなら`run_all.sh <OUT> s4`で前半の写しを使い回せる。
  - 形は測って確かめる：`python3 tools/hakaru.py`（レイヤーと u・v・z の範囲で物を探し、寸法・高さ・離れを出す）。見比べの絵は`python3 tools/kuraberu.py`（名前つきの視点`tools/views.json`で、今と案を並べる。先に`bash model/build/setup.sh`、1枚約40秒、同時に2本は走らせない）。使い捨ての測るスクリプトや絵のコードを毎回書かない。
- 通しの確かめは `bash tools/tsukuru.sh`（ログはファイルへ、出すのは check の行と止まった所だけ）。Bash の run_in_background で走らせ、終わりの知らせを待つ。途中で何度も覗かない。
- **push も一連の直しの区切りで**：main への push のたびに自動の作り直し（30〜40分）が走り、走っている間の push は一つの待ちにまとまる。直すたびに push すると、ほかの係の作り直しも待たされる。commit は直すたびに、push は区切りで（ただし二つの係が持つファイル`run_exact_new.py`・`add_hall.py`・`fix_details.py`は、直したらすぐ push：役割分担の「3dmのスクリプト」）。
- 長い文書は見出しから：`python3 tools/yomu.py <file>`（見出しと字数）→ `python3 tools/yomu.py <file> 見出しの一部`（その節だけ、`--grep 語` で行だけ）。
- スクリプトは `grep -n` で場所を探し、Read の offset・limit で要る所だけ。一度読んだ所は会話に残っているので、二度読まない。
- 図は縮めた画像（長辺 1600 px 以下）を、確かめたい所だけ切り抜いて1枚ずつ。見比べのために何枚も取り込まない（見比べはサブエージェントに）。
- **図の書き出しはPDFだけ**（10-31、ユーザー：.png・.svg・.aiを毎回作るのは無駄）：リポジトリに置く図は、文字を文字のまま（Type42）埋め込んだPDF一つ（Illustratorでそのまま開ける）。確かめ用の画像（PNG）は`/tmp/claude-0/`に作って見るだけで、commit しない。SVGはレーザーのデータ（`mokei/`）とロゴの元データだけ。写真やレンダリングのように元から画像のものは別。
- 書いたファイル・文書を、確かめのために読み直さない（Edit・Write は失敗すれば知らせる）。

## 3. 決定事項は直す所だけ
- **今の決まりだけを書く**（覆された案・経緯・測った途中の数は変更の記録`inbox.py log`とgitへ）。分冊は新しいチャットが始めに丸ごと読むので、長いほど毎回重い。目安は2万字以内。
- 10-28 から決定事項はリポジトリの `kettei/` が本文（共通は `kyoutsu.md`）。読むのは `tools/yomu.py` で節だけ、書くのは Edit で直す所だけ（全文を読み直して全文を書かない）。
- プロジェクトの文書は写し。写しを作るときは `project_write` の `local_path`（中身が会話に入らない）。

- **知らせは少なく短く**：知らせ1件ごとに、あて先のチャットが読む量が増える。あて先の作業が変わるときだけ出し、1行で（理由・経緯は自分の決定事項に書いて名前で指す）。決まりの文書（karuku.md・役割分担）の小さな直しは知らせない（新しいチャットは始めに読む）。

## 4. 頼みが変わったら新しいチャット
- 一つの頼みが済んで、次の頼みが別の場所・別の作業（壁→屋根の形→大きさ）なら、新しいチャットで始める方が軽い。決まりを書いて push しておけば、引き継ぎは要らない（新しいチャットは決定事項と git log を読む）。
- 重さを測りたいときは `explain-usage`（このセッションの量の内訳）。
